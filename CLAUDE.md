# Currency Advisor — правила работы в репозитории

Сервис анализирует курс RUB → AMD и рекомендует пользователю менять валюту
сейчас или подождать, с объяснением "почему". Не предсказывает будущее —
оценивает вероятность выгодного момента по набору факторов. Архитектура
должна допускать подключение ML-модели позже без переписывания.

Полный план этапов и архитектурные обоснования — в [ROADMAP.md](ROADMAP.md).
Этот файл — стабильные правила, которые не меняются от этапа к этапу.

## Стек

Python 3.13 (менять на более старую версию только при объективной
технической причине) · FastAPI · SQLAlchemy Async · Alembic · PostgreSQL ·
asyncpg · Docker / Docker Compose · aiogram · pytest · Ruff · mypy (strict) ·
pre-commit · uv.

## Структура

```
app/
  api/          — FastAPI роуты, без бизнес-логики
  collectors/   — внешние источники данных, никакого IO в БД
  core/         — конфиг, логирование
  db/           — engine/session
  models/       — SQLAlchemy-модели
  repositories/ — единственный слой с доступом к БД
  schemas/      — Pydantic-схемы API
  services/     — бизнес-логика, связывает Collector/Repository
  bot/          — Telegram bot, вызывает services, не трогает SQLAlchemy-модели
alembic/
tests/
docker/
.github/
```

## Архитектурные границы (обязательны)

- Collector не пишет в БД.
- Repository не ходит во внешние API.
- API-слой не содержит бизнес-логику.
- Telegram Bot не работает с SQLAlchemy-моделями напрямую, только через services.
- Денежные/курсовые значения — только `Decimal`, никогда `float`.
- Время — с timezone, внутри системы UTC.
- Новый источник данных реализует контракт `RateCollector.collect() -> list[RatePoint]`
  из `app/collectors/base.py`. Отдельного слоя нормализации нет —
  нормализация является частью этого контракта.
- Не добавлять абстракции/паттерны без действительной необходимости, но
  контракт Collector должен оставаться стабильным при добавлении новых
  источников — без переписывания бизнес-логики.

## Git-flow

Ветки: `main` (стабильная), `develop` (интеграционная). Функциональность
разрабатывается только в `feature/*`, `chore/*`, `docs/*`, `fix/*` от
актуального `develop`. Прямые коммиты в `main` и `develop` не делаются.

```
git switch develop
git pull origin develop
git switch -c <type>/<task-name>
git push -u origin <type>/<task-name>
```

Перед началом любой работы — проверить текущую ветку
(`git branch --show-current`), не работать в `main` по ошибке.

Направление слияния: `feature/* → develop → main` (в `main` — только по
завершении полноценного этапа/релиза), всегда через Pull Request.

## Коммиты

Conventional Commits (`feat`, `fix`, `test`, `refactor`, `style`, `docs`,
`chore`, `ci`, `build`). Один коммит — одно осмысленное изменение; не
смешивать новую функциональность, массовое форматирование, несвязанные
фиксы, инфраструктуру и рефакторинг в одном коммите. Не использовать
`git add .` не глядя, если изменения затрагивают несколько несвязанных
файлов — добавлять конкретные файлы. Никаких пустых сообщений (`update`,
`fix`, `wip`).

## Обязательные проверки перед коммитом/PR

```
uv run ruff check .
uv run ruff format --check .
uv run mypy app
uv run pytest
```

PR не считается готовым к merge, пока GitHub Actions не прошёл зелёным —
локально пройденные проверки этого не гарантируют, проверять реальный
прогон workflow после push.

## Как подходить к задачам в этом репозитории

- Не перепрыгивать через этапы `ROADMAP.md` и не писать код на будущие этапы.
- Если структура существующего файла неясна или есть расхождение между тем,
  что описано, и тем, что реально в репозитории — сначала прочитать и
  спросить, не переписывать вслепую.
- Перед архитектурными решениями (новая абстракция, новая зависимость, смена
  версии инструмента) — кратко объяснить решение и файлы, которые оно
  затронет, до того как писать код.
- Не отключать проверки/не исключать код из Ruff/mypy/pytest ради зелёного
  CI без архитектурной причины.
