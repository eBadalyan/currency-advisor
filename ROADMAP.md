# Currency Advisor — Roadmap

Сервис анализирует курс RUB → AMD и подсказывает пользователю: менять валюту
сейчас, подождать, сколько примерно ждать и почему. Система не предсказывает
будущее — она оценивает вероятность того, что текущий момент выгоден, на
основе набора факторов. Архитектура должна допускать подключение ML-модели
позже без переписывания системы.

## Архитектура

```
Источники данных (SOAP ЦБ Армении, Trading Economics, ЦБ РФ, MOEX, ...)
        │
        ▼
   Collectors            — получение сырых данных, retry/timeout, никакого IO в БД
        │  (нормализация встроена в контракт Collector: collect() -> list[RatePoint])
        ▼
   Repository             — единственная точка доступа к БД, никаких внешних запросов
        │
        ▼
   PostgreSQL
        │
        ▼
   Analytics Layer        — скользящие средние, волатильность, локальные min/max
        │
        ▼
   Recommendation Engine  — оценка "менять/ждать" + объяснение по факторам
        │
        ▼
   API / Telegram Bot     — общий Service-слой, без прямого доступа к SQLAlchemy-моделям
        │
        ▼
   Пользователь
```

Границы слоёв фиксированы: Collector не пишет в БД, Repository не ходит во
внешние API, API-слой не содержит бизнес-логику, Bot не работает с
SQLAlchemy-моделями напрямую.

## Статус

Инфраструктурный этап завершён (FastAPI, SQLAlchemy Async, Alembic, Docker,
CI, pre-commit). Отдельный PR `chore/cleanup-legacy-scaffold → develop`
убирает нерабочий каркас первого коммита (`app/providers/*`,
`app/services/rate_service.py`, дублирующий `app/api.py`, дублирующий CI-workflow)
и подключает mypy strict в CI/pre-commit — должен быть влит до начала Этапа 1.

Следующий шаг: **Этап 1 — Collector ЦБ Армении**, ветка `feature/cba-collector`.

## Этапы

### Этап 1 — Collector ЦБ Армении
- **Ветка:** `feature/cba-collector`
- **Файлы:** `app/collectors/cba.py`
- **Что делает:** подключение к SOAP API ЦБ Армении, получение RUB/AMD и
  USD/AMD, retry, timeout, структурированное логирование.
- **Контракт:** реализует `RateCollector.collect() -> list[RatePoint]` из
  `app/collectors/base.py`. Нормализация — не отдельный слой, а часть
  контракта: любой коллектор обязан отдавать `RatePoint`
  (source/base_currency/quote_currency/value: Decimal/observed_at). Общий
  `app/collectors/normalization.py` заводится только когда у 2+ коллекторов
  реально появится дублирующаяся логика (ожидаемо — Этап 8).
- **Прежде чем писать код:** свериться с реальным WSDL ЦБ Армении
  (`api.cba.am/exchangerates.asmx?wsdl`) — предыдущая (удалённая) реализация
  никогда не проверялась против живого API.
- **Design notes:**
  - HTTP через `httpx` (async-native), retry — `tenacity` как задекларированная зависимость.
  - Своя иерархия исключений коллектора (`CollectorTimeoutError`,
    `CollectorResponseError` и т.п.) — единый способ для Service-слоя позже
    обрабатывать сбои разных источников одинаково.
  - HTTP-клиент инжектируется в конструктор, тесты мокают транспорт
    (`httpx.MockTransport`), без походов в реальный SOAP API.
  - Таймаут/число попыток — через `Settings` (env), не хардкод.
  - Завести переиспользуемый контрактный тест
    (`assert_collector_contract(collector)`), которому будет обязан
    соответствовать любой следующий коллектор (Этап 8).
- **Не делать на этом этапе:** сохранение в БД, Repository, Service, API,
  Bot, ML.

### Этап 2 — Repository
- **Ветка:** `feature/exchange-rate-repository`
- **Файл:** `app/repositories/exchange_rate.py`
- **Методы:** `save()`, `bulk_save()`, `get_latest()`, `exists()`, `find_by_date()`.
- Единственный слой, которому разрешено обращаться к БД напрямую. Не должен
  знать о существовании внешних API.

### Этап 3 — Service
- **Ветка:** `feature/rate-service`
- **Файл:** `app/services/rate_service.py`
- Связывает Collector и Repository: `collect → save`.
- **Definition of Done включает бывший "Этап 5":** проверка полной цепочки
  получение → сохранение → чтение обратно на реальной БД. Отдельной ветки
  под это не заводим — это критерий готовности Service, а не отдельная
  функциональность.

### Этап 4 — Периодический запуск сбора данных *(новый этап)*
- **Ветка:** `feature/rate-scheduler`
- **Почему нужен:** Analytics (скользящие средние, волатильность) и
  Recommendation Engine требуют накопленной истории за дни/недели. Redis/Celery
  запланированы на потом, но ждать полного стека для банального "запускать
  раз в N минут" — значит потерять время на накопление данных. Лёгкий
  шедулер (`APScheduler` в lifespan FastAPI, либо cron-контейнер) закрывает
  разрыв до появления Celery.
- **Важно:** запускать сразу после Этапа 3, параллельно с разработкой
  Этапов 5–7 — чем раньше стартует накопление истории, тем меньше простоя
  перед Analytics/Recommendation.
- Celery + Redis подключаются позже, когда появится несколько независимо
  расписанных источников с ретраями/распределением задач (после Этапа 8) или
  тяжёлый фоновый пересчёт рекомендаций.

### Этап 5 — API
- **Ветка:** `feature/rate-api`
- **Методы:** `GET /latest`, `GET /history`.
- Проверка через Swagger. Никакой бизнес-логики в роутах — только вызов Service.

### Этап 6 — Telegram Bot (базовый)
- **Ветка:** `feature/telegram-bot`
- **Команды:** `/start`, `/rate` — чтение курса из БД через тот же
  `RateService`, что использует API (общий Service-слой, вызываемый как
  обычная функция в процессе — не отдельный HTTP-вызов в свой же API; вопрос
  вынесенного деплоя бота отдельно от API — решение на будущее, не сейчас).

### Этап 7 — Второй источник + сравнение
- **Ветка:** `feature/cbr-collector`
- **Источник сменён с Trading Economics на ЦБ РФ:** Trading Economics
  требует платного API-ключа (публичный `guest:guest` выведен из обращения,
  `HTTP 410 Gone` при проверке) — реализовать и проверить вживую, как CBA,
  было бы нельзя. ЦБ РФ (`https://www.cbr.ru/scripts/XML_daily.asp`) —
  официальный, бесплатный, без авторизации, уже значится в списке основных
  источников проекта.
- Собирает **USD/RUB** (не RUB/AMD напрямую) — мостовая пара для будущего
  синтетического RUB/AMD через USD (Этап 8/9): `synthetic_rub_amd =
  usd_amd.value / usd_rub.value`, сравнение с официальным RUB/AMD от ЦБ
  Армении и есть то самое "сравнение источников".
- Технические особенности API ЦБ РФ (проверено вживую перед реализацией):
  ответ в `windows-1251`, а не UTF-8 — парсинг из raw bytes, чтобы
  `ElementTree` сам применил кодировку из XML-декларации; `Value` использует
  запятую как десятичный разделитель; `Nominal` не всегда `1` (для части
  валют — на 100 единиц). Дата запроса — по московскому календарному дню
  (`Europe/Moscow`), тот же паттерн, что и Ереван для CBA.
- Реализован как второй `RateCollector`, прогоняется через контрактные
  тесты из Этапа 1 (`assert_returns_valid_rate_points`).
- **Design note, решено:** признак "официальный/рыночный" в `exchange_rates`
  не добавляется — оба источника публикуют официальные курсы своих
  центробанков (не рыночные котировки), различие по надёжности здесь не
  актуально. Резолюция данных (оба — раз в календарный день) решается на
  уровне `source`, как и предполагалось.
- Не блокирует и не блокируется Этапом 8 (Analytics) — может вестись параллельно.

### Этап 8 — Analytics Layer
- **Ветка:** `feature/rate-analytics`
- Скользящие средние, изменение курса, волатильность, локальные min/max.
- **Зависит только от Repository + накопленных данных** (Этапы 2–4), не от
  API/Bot/второго источника — можно начинать сразу после того, как в БД
  появится достаточно точек, не дожидаясь Этапов 5–7.

### Этап 9 — Recommendation Engine *(новый этап — ключевой пробел исходного плана)*
- **Ветка:** `feature/recommendation-engine`
- **Почему это отдельный обязательный этап:** это ядро продукта — то, ради
  чего сервис существует ("менять сейчас / ждать / почему"). Ни один из
  предыдущих этапов явно не создаёт эту логику; Bot из Этапа 6 отдаёт только
  сырой курс.
- **Design notes:**
  - Проектировать как интерфейс/стратегию (`RecommendationStrategy` с
    методом вроде `evaluate(history) -> Recommendation`), а не как одну
    функцию с формулой — тогда rule-based версия (на индикаторах из Этапа 8)
    и будущая ML-модель — две реализации одного контракта, без переписывания
    Bot/API.
  - `Recommendation` — структура с разложением по факторам
    (`RecommendationFactor`: имя, вес, значение), а не голое число/строка.
    Даёт объяснимость ("почему") бесплатно и одновременно становится
    вектором признаков для будущей ML-модели.
  - Логика синтетического кросс-курса и отклонения между источниками
    (была в удалённом `RateService`, архитектурно не туда положена)
    возвращается сюда, уже на правильном слое.
- Bot получает новую команду (например `/advice`), использующую этот движок
  поверх Этапа 6.

### Далее (не детализировано)
- Армянские банки, Rate.am, новости, экономический календарь — новые
  Collectors по контракту Этапа 1.
  - Банки (Этап "Далее", в работе): Ameriabank, Evocabank, ACBA Bank, VTB
    Армения подключены как `RateCollector` — скрапинг курса наличной покупки
    (cash buy) RUB, без официального API у самих банков (проверено вживую).
    Rate.am и Fast Bank отклонены: данные грузятся клиентски через
    недокументированный протокол (Next.js Server Actions / нет статики),
    нестабильный контракт.
  - Экономический календарь (важность новостей по валютам, ForexFactory-стиль)
    — исследовано и отложено (2026-07-21): у ForexFactory нет API; FXStreet
    закрыт OAuth2 без публичного self-serve тарифа; Trading Economics,
    Financial Modeling Prep и Finnhub — у всех троих сам календарь платный
    (проверено вживую реальными ключами, включая FMP/Finnhub, где free-тариф
    есть для других эндпоинтов, но не для календаря). Неофициальные зеркала
    существуют, но несут тот же риск нестабильного контракта, что и
    Rate.am/Fast Bank. Возвращаться к этому пункту только если найдётся
    настоящий бесплатный официальный источник, либо будет принято решение
    платить за один из проверенных.
  - Банковский рыночный сигнал в Recommendation Engine (в работе,
    2026-07-21): `BankAverageService` считает медиану (не среднее — банки
    выбраны как раз потому, что обычно дают лучший курс, выборка заведомо
    смещена, медиана устойчивее к выбросам) курса по 4 банкам, с порогом
    минимум 2 отчитавшихся банка, и сохраняет как отдельный производный
    `RatePoint` (`source="Bank Average (RUB cash, derived)"`). Используется
    в `RuleBasedRecommendationStrategy` пока только как информационный
    фактор (`weight=0`, не влияет на action/confidence) — официальный курс
    ЦБ Армении отличается от него структурно (~20-25%, не аномалия, а
    последствие ограниченной ликвидности наличного RUB в Армении после
    2022 года).
    **Следующий шаг, когда накопится история**: переключить основной
    сигнал тренда/скользящей средней с CBA на Bank Average. Обязательное
    условие перед этим переключением — `AnalyticsService.get_indicators`
    сейчас использует `window` как `LIMIT` (число строк), а не диапазон
    дат. CBA пишет ~1 строку/день (дедуплицируется по календарному дню),
    банки и их агрегат пишут с интервалом шедулера (~48 строк/день) — при
    прямом переключении `window=30` даст ~15 часов вместо ~30 дней. Нужно
    сначала научить `AnalyticsService` принимать окно по датам (`since=`),
    а не по количеству строк, иначе переключение будет тихо сравнивать не
    те периоды.
- MLflow/CatBoost — конкретная реализация `RecommendationStrategy` из Этапа 9.
- Redis/Celery — когда потребуется полноценная распределённая очередь задач,
  не раньше.
- Retention/партиционирование `exchange_rates` — обозначить как задачу
  до перехода на непрерывный многоисточниковый сбор (после Этапа 7).

## Изменения относительно исходного плана

| Было | Стало | Причина |
|---|---|---|
| Этап 4 — Normalization отдельным этапом | Убран | Уже часть контракта `Collector.collect() -> list[RatePoint]` |
| Этап 5 — первое сохранение отдельной веткой | Слит в DoD Этапа 3 (Service) | Это критерий приёмки, а не функциональность |
| Analytics после API/Bot/второго источника | Analytics зависит только от Repository | Не нужно ждать 5–7, чтобы считать индикаторы по уже сохранённым данным |
| Планирование через Celery "потом" | Добавлен Этап 4 — лёгкий шедулер сразу после Service | Без периодического сбора не накопится история к моменту Analytics/Recommendation |
| Recommendation Engine — только на диаграмме, без этапа | Добавлен явный Этап 9 | Это ядро продукта, отсутствовавшее в детализированном плане |
